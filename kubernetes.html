Integrations · Kubernetes

Identities, not guesses

EffectTrace connects actions to Kubernetes objects through identifiers that Kubernetes already guarantees: server-generated audit IDs, object UIDs, resourceVersions and controller ownerReferences matched by UID.

The audit log, at Metadata level

  • EffectTrace reads ResponseComplete events of mutating verbs and reduces them to request metadata. The lab audit policy never goes above Metadata: no request or response bodies.
  • A successful, non-dry-run mutation not claimed by a tool call becomes its own KUBERNETES_API_CALL action, which is how a human kubectl scale gets its own graph.
  • Controller identities and ignored resources do not become actions.

Audit-ID: read, never set

kube-apiserver accepts a client-supplied Audit-ID header without validation, so a client-chosen ID could collide with or impersonate another request. pkg/k8sinstrument therefore never sets the header: it only reads the value the server echoes in the response. The audit event is used as confirmation only when it agrees on verb, resource, subresource, namespace and name.

UID first, names last

The target of a request is resolved in a fixed order, and the rule used is recorded on the edge.

OrderSourceRule recorded
1UID and resourceVersion in the response seen by the instrumented clientuid-from-client-response
2objectRef.uid in the audit eventuid-from-audit-object-ref
3The only object of that kind, namespace and name alive at request timeuid-resolved-by-name-at-request-time
–No match, or more than one matchtarget-not-observed (no UID asserted)

ownerReferences by UID

Deployment → ReplicaSet → Pod (and StatefulSets, DaemonSets, Jobs) is followed through controller ownerReferences matched by UID, inside the action's reconciliation window, only when no other action claims the change.

Same name, new UID

Names are descriptive and can be reused after deletion. When several objects carried a name around the request time, name resolution refuses to guess; a recreated object with a new UID is never confused with the old one.

No-op requests

A successful request does not always change anything. Fan-out is attributed only to mutations whose change was actually observed, for example a generation increase on workload kinds.

What is watched, and what never is

The collector watches only what it needs to follow controller ownership and rollout progress, and strips objects to identity, ownership and rollout status before they enter the informer cache.

Watched (get/list/watch)Never watched
Deployments, ReplicaSets, StatefulSets, DaemonSets, JobsConfigMaps
Pods, ServicesSecrets
core/v1 Events (reason, type, sanitized note, count)Request and response bodies

ConfigMap and Secret contents are frequently sensitive, and Kubernetes records no ownership from them to the Pods that consume them, so watching them would add exposure without adding evidence. A request that changes a ConfigMap is still recorded as DIRECT when the instrumented client reports its UID; it simply has no structural fan-out.
